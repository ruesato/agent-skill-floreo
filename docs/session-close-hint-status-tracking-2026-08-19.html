    Key Decisions

    • Status enum over parallel booleans — chose status="pending|approved|resolved|rejected" over separate boolean attributes (resolved="true", approved="true"). States are mutually exclusive in a revision cycle; an enum is self-documenting and extensible.
    • Backward compatibility with applied="false" — legacy syntax continues to work as an alias for status="rejected" (without a reason). Existing drafts don't break; new drafts should prefer status="rejected" for clearer semantics.
    • resolved strips silently; rejected preserves as comment — resolved means the author already fixed the underlying issue by editing content, so the hint is no longer relevant and is stripped without a trace. rejected means the author considered and declined it, so the decision is preserved as <!-- floreo:hint (rejected): … — reason --> for reviewer visibility.
    • No summary callout in v1 — the "see what's pending vs. acted on" UX is satisfied by the author reading state in the source markdown. A rendered summary surface (e.g., a review callout listing pending hints) is deferred to a follow-up issue if needed.
    • Optional reason attribute on rejected — status="rejected" reason="…" captures why a hint was declined; the reason is included in the preserved HTML comment. Not required, but recommended for revision-cycle traceability.

    Blockers & Open Questions

    • No test suite — floreo is a prompt-based Claude Code skill, not runtime code. There are no automated tests. The fixture (docs/baseline/hint-states-example.md) is a reference example, not a programmatically verified test. Render behavior must be validated manually by rendering the fixture with /floreo.
    • check-floreo.sh does not validate markdown source — the validator checks rendered HTML output, not draft .md files. Extending it to validate status attribute values in markdown is a future enhancement.
    • Summary callout deferred — if users find source-markdown state tracking insufficient for revision cycles, a rendered summary surface (listing pending hints in a callout) could be added as a follow-up.
