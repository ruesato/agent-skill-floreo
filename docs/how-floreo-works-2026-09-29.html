How Floreo Works

Floreo is a Claude Code skill that turns what an AI agent writes into a single, self-contained web page that people can read, print, and keep.

Contents

    What Floreo Is

    Floreo is an agent skill for Claude Code, Anthropic's coding assistant for the terminal. An agent skill is a set of written instructions, plus any scripts they need, that the agent loads when a task calls for it. Floreo's instructions teach the agent to take a report, plan, incident review, or session summary it has written and publish it as one HTML file with a design system built in. The name is Latin for "I flower."

    The people reading these documents are a mix. Engineers and technical leads scan them during a work session and want to find the signal quickly. Managers, product leads, and other stakeholders read proposals and analyses from start to finish to make a decision. Floreo tries to serve both readers on the same page, with clear entry points for scanning and a coherent order for reading straight through.

    Why I Built It

    Agents write Markdown by default. Markdown works well in source control, but it is a poor surface for reading. It has no visual hierarchy, its tables are hard to scan, and it has no charts, no side navigation, and no print layout. For a document a person actually reads, that format undersells the work that went into it.

    I wanted every agent document to land in the same visual system, with typography, color, dark mode, and responsive layout already decided. A post-incident review written at the end of a session should read like something a designer laid out. The page also had to work with no network connection and no external files, so it can be attached to an email, archived, or opened a year later and look the same.

    The second audience is other agents. A floreo document carries its own structure: stable section IDs, metadata tags, and a copy of the plan it was built from. A later agent can update the document without reverse-engineering its markup.

    How a Document Gets Made

    Floreo drafts first by default. Asking for a document produces a floreo Markdown draft in the project's docs/ folder. The agent then stops and reports how many sections and rich elements the draft contains. You can edit the draft by hand or ask for changes, and say "render" when it is ready.

    Rendering runs in up to three phases. In Phase 1, the main model works out who the document is for, what order the information should come in, and which visual treatment fits each section. It writes a Content Plan: a plain-text outline with the title, audience, purpose, accent color, and every section's content. In Phase 2, a smaller, cheaper model (currently Haiku) turns the Content Plan into HTML. That step is mechanical, so there is no reason to spend a larger model on it. Phase 3 runs only when the impeccable design skill is installed and the project has a PRODUCT.md file describing its users and brand. It makes a visual quality pass on the finished page.

    Draft first, one shot second

    The first release rendered HTML in one pass. That suited documents written once, but every revision meant regenerating the whole page with its template. In version 1.2.0 I added a Markdown draft format, and in 1.2.1 I made drafting the default, so revision rounds happen in a small text file and the HTML is built once at the end.

    One-shot rendering is still there when you ask for it ("skip the draft" or "just give me the HTML"). Session-close summaries and agent briefs always go straight to HTML, because they are single-pass handoff documents where a draft adds nothing.

    The Four Skills

    The plugin installs four commands. Most people only use the first one.

    CommandWhat it does
    /floreoDrafts a document from a description, or renders an existing draft when given its path.
    /floreo:draftWrites only the Markdown draft, for content that is still being shaped.
    /floreo:setupAdds a rule to the project's CLAUDE.md, the instructions file Claude Code reads at the start of each session, so the agent uses floreo for reading documents without being asked.
    /floreo:unsetupRemoves that rule.

    The Draft Format

    A floreo draft is ordinary Markdown with three additions. It stays readable in any editor and costs little to revise.

    • Frontmatter. A short header block at the top of the file sets the title, the document type, the accent, and interactive features such as a table of contents.
    • Intent blocks. Fenced blocks whose label names a component, such as chart:bar, diagram:flow, callout:warning, or stat-block. The draft says what the element is and what data it holds, and rendering decides how it looks.
    • Hints. <hint> tags carry instructions for the render step, like "horizontal layout, highlight Q3 as the peak." They never appear in the final page.
    ---
title: Q1 Performance Review
type: report
accent: technical
interactive: toc
---

## Revenue

```chart:bar
labels: [Q1, Q2, Q3, Q4]
data: [42000, 58000, 71000, 63000]
<hint>horizontal layout, highlight Q3 as the peak</hint>
```

    Hints can carry a status, so a revision round leaves a record of what was accepted and what was declined.

    StatusWhat rendering does
    none, pending, or approvedApplies the hint, then removes it from the page.
    resolvedRemoves it without applying it, because the author already made the change.
    rejectedSkips it and keeps it as an HTML comment, along with the reason if one was given.

    What Is Inside a Document

    Every floreo document is one .html file. Styles go in the head, any JavaScript goes at the end of the body, and charts are inline SVG (scalable vector graphics, drawn in code instead of embedded as images). Nothing loads from the network. Size budgets keep pages small: 20 KB for a session summary, 30 KB for an incident report, 50 KB for a research brief, and 100 KB at the most.

    Three conventions exist for the agents that come later.

    Metadata tags
    floreo:type, floreo:created, floreo:model, and floreo:version in the page head, so documents can be cataloged and searched.
    Section IDs
    A data-floreo-id slug on every section, taken from its heading. It gives stable links and section-level diffs across versions.
    Content Plan
    The plan the page was built from, embedded in a script tag of type application/floreo. Browsers ignore it. A later agent reads it to update the document.
    document.querySelector('[data-floreo-id="constraints"]').textContent

    The markup is compressed on purpose, with no indentation, no comments, and optional closing tags left out. People only ever see the rendered page, and agents pay for every character of source they read.

    The Design System

    The design system is called The Reference Shelf. Pages should feel like books you keep and come back to. It uses warm stone neutrals, flat surfaces with no shadows, and one accent color per document that changes with the type: red for incidents, violet for decisions, cyan for research, and green for retrospectives.

    • Three type voices. A book serif for the title and section headings (Charter, falling back to Georgia), the system sans-serif for body text and sub-headings, and the platform's code font for labels, timestamps, and code. All three are fonts already installed on the reader's machine.
    • Dark mode. Pages follow the reader's system setting, and every color has a dark counterpart.
    • Components. Fourteen building blocks: callouts, tables, card grids, code blocks, key-value lists, status badges, stat rows, timelines, numbered procedures, before-and-after splits, collapsible sections, diff tables, inline code, and the table of contents.
    • Charts. Nine inline SVG patterns: bar, grouped or stacked bar, line, area, scatter, donut, heatmap, milestone, and flow diagram. Every chart has a title and description for screen readers, and every data color meets the 3:1 contrast minimum in the Web Content Accessibility Guidelines (WCAG).
    • Reading interface. An optional add-on for long documents, with in-page search that steps through matches, a sticky table of contents, and a copy-as-Markdown button.

    The September design pass

    On 2026-09-29 I ran the impeccable design skill's critique on the template. It scored the template 27 out of 40. It found that dark mode broke on diff tables and code blocks, and that metadata text measured 2.41:1 against the page, well under the 4.5:1 WCAG minimum for body text. It also found that some components used patterns the design system itself bans, such as colored side stripes on the diff table.

    The fixes replaced hard-coded colors with tokens, raised text contrast in both themes, rebuilt the stat row, diff table, and cover header, and refined the type and spacing. A second critique scored 30 out of 40, and the automated detector found nothing.

    Tooling

    Three shell scripts ship with the repository. The first two work on documents; the third works on the skills themselves.

    ScriptWhat it does
    check-floreo.shChecks documents against the quality checklist: metadata tags, no external files, the embedded Content Plan, section IDs, chart accessibility, dark-mode overrides, size budget, and hard-coded colors. The exit code makes it usable as a build gate.
    migrate-floreo.shKeeps a folder of documents current when the template changes. report lists every document, extract pulls each Content Plan out for a clean re-render, and refresh-css swaps in the current base styles and keeps a backup.
    scan-skills.shRuns NVIDIA SkillSpector, a security scanner for agent skills, over everything in skills/. Continuous integration (CI) runs it on every push and pull request, and the build fails on any finding that hasn't been reviewed.

    The security scan exists because agents run these scripts with implicit trust. The migration script rewrites HTML files, and the setup skills edit the project's CLAUDE.md. Each suppressed finding in the baseline file has a written reason, and a suppression stops working if the excused text or the scanner version changes, so it comes back for another review.

    Installing Floreo

    Claude Code plugins install in two steps: register the marketplace, then install the plugin. This installs floreo for every project on the machine. Adding --scope project limits it to one project.

    /plugin marketplace add ruesato/plugins
/plugin install floreo@ruesato-plugins

    To work on floreo itself, start Claude Code with the local clone, and run /reload-plugins after editing a skill file.

    claude --plugin-dir /path/to/agent-skill-floreo
    Tip: Run /floreo:setup once in a project if you want every report, plan, and summary there to come out as a floreo document without asking for it.

    When Not to Use It

    Floreo is for documents that exist to be read. It stays out of files whose format a project or tool depends on.

    • Project Markdown files. README.md, CLAUDE.md, AGENTS.md, CONTRIBUTING.md, and anything else the project expects in Markdown.
    • Skill and config files. SKILL.md, command and agent definitions, and rules files for coding tools.
    • Machine input. Anything another agent or tool will parse as plain text.
    • Short answers. Replies of one to three sentences, quick status updates, and inline code explanations.
    • Text headed somewhere else. Pull request descriptions, GitHub comments, and pages bound for Notion or Confluence.

    A document qualifies when it has at least two of these: three or more sections, a table or chart, a reason to persist past the conversation, or readers beyond the person who asked for it.
